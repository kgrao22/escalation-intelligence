01

What it does

Every day, people post problems into a Slack channel called #escalations. Over a year that is 600 conversations. Nobody has time to read them all, so patterns hide in the pile.

This project reads that pile and produces a short, evidence-backed review for leadership. It does that by answering two separate questions about every single conversation:

  1. Is this a technical fault? Something is broken in the product.
  2. Is this a repeatable manual task? Someone asked an engineer to do something by hand that a tool could do.

Those two questions are genuinely independent. A conversation can be one, both, or neither. That insight is the heart of the design, and we will come back to it constantly.

The output is a Slack post: one summary message plus four threaded replies, written for people who will never look at the code.

The one-sentence version

It turns a year of messy Slack chatter into a ranked list of things to fix and things to automate, with a link to the original conversation behind every claim.

The vocabulary

The project invented a handful of words. If you learn these eight, everything else reads easily.

WordWhat it means
ThreadOne Slack conversation: an opening message plus all its replies. The basic unit of everything.
ExtractionReading one thread with an AI and filling in a structured form about it: is it technical, how severe, what system, is it a repeatable manual task.
EmbeddingTurning a sentence into a list of 1,024 numbers, so a computer can measure how similar two sentences are.
AdjudicationAsking the AI a yes/no-ish question about two threads: are these the same underlying issue?
Group / clusterA set of threads judged to be the same recurring thing. A group of 8 means it happened 8 times.
WindowHow far back we looked: 90d, 180d, 365d. Every file is stamped with its window so they never get mixed up.
ArtifactA JSON file written to disk by one stage and read by the next. The pipeline is a chain of these.
ProvenanceThe record of which exact file a result came from. Used to stop stale results leaking between runs.
03

System overview

Here is the whole thing on one page. Read it left to right. Notice that after extraction the pipeline splits into two parallel tracks that never touch each other, then rejoins only at the very end to produce the review.

Two things worth noticing straight away:

  • Each stage is a separate command. You run them one at a time. Nothing is a long-running service. If a stage fails, you re-run only that stage.
  • Each stage writes a file. That file is the input to the next stage. This means you can inspect, audit, or replace any step without re-doing the expensive ones.
04

The two tracks

This is the single most important design decision, so it gets its own section.

When someone posts "the renewal email didn't send", that is a bug. When someone posts "can you please change this customer's email address in the backend", that is not a bug at all — the product is working exactly as designed. It is a repeatable manual chore.

An early version of this project only tracked bugs, and threw away every "please do this for me" request. That deleted the entire category of work that automation could remove. So the extraction step now makes two independent judgements, and the pipeline runs two separate analyses.

Track A — Technical faults

Threads where isTechnicalEscalation = true.

  • Embeds the problem statement ("invoice tax is calculated wrongly")
  • Asks: "are these the same underlying issue?"
  • Produces: recurring defects to fix

Track B — Manual workflows

Threads where isAutomationWorkflowCandidate = true.

  • Embeds the workflow statement ("update a customer's email across systems")
  • Asks: "are these the same repeatable task?"
  • Produces: manual work to automate

All four combinations are legitimate, and the numbers from the real 365-day run show all four occur in volume:

CombinationMeaningThreads
Technical onlyA bug with no manual workaround143
Workflow onlyAn operational request, not a bug170
BothA bug whose standing workaround is a manual fix110
NeitherA question, or a one-off187
Why the tracks must never mix

The two tracks embed different sentences. If you put "invoice tax is wrong" and "update a customer's email" into the same similarity pool, you manufacture false neighbours. The code physically refuses this: assertEmbeddingCandidatesSafe throws if a batch contains a mix, and the files use different name prefixes so one can never be read as the other.

Note also that 110 threads appear in both tracks. That is correct and intentional. But it means you must never add "240 technical + 280 workflow" together and call it 520 issues — the real number of distinct actionable threads is 410. The review computes this union explicitly to avoid double-counting.

05

The pipeline, stage by stage

Ten stages. For each: what goes in, what happens, what comes out, and which API it costs money on.

01

Fetch the threads

Calls Slack's history API, walks each conversation, pulls every reply, and filters out bot noise like Jira sync messages. Writes one big JSON file of clean threads.

Slack API · read in: channel + days out: escalations-365d-*.json
02

Extract structured facts

One AI call per thread. Reads the conversation and fills a strict form: is it technical, severity, affected system, resolution status, and the workflow questions. This is where the two tracks are born. 600 threads = 600 calls, though 260 were reused from an earlier run because the text was byte-identical.

Anthropic · 340 calls in: threads out: extractions-365d-*.json
03

Embed the statements

Sends only the short, de-identified statements to Voyage, which returns 1,024 numbers per sentence. Runs twice — once per track, into two separate files. Cheap: 240 + 280 sentences is about 5 API calls total.

Voyage · ~5 calls out: embeddings-365d-*.json out: workflow-embeddings-365d-*.json
04

Generate candidate pairs, then adjudicate

Compares every possible pair of embeddings locally (28,680 pairs for the technical track) and keeps only those above a similarity floor. Then asks the AI about each survivor: same issue, related family, or different? The floor is not a decision — it only decides which questions are worth paying to ask.

Anthropic · 1,400 + 290 calls pair maths: local out: adjudications-365d-*.json
05

Build groups and clusters

Turns thousands of pairwise verdicts into actual groups using graph algorithms. No AI, no network — pure deterministic maths. This stage had a serious quality bug at year scale, covered in section 09.

fully local out: groups-365d-v2-*.json out: workflow-clusters-365d-v2-*.json
06

Rank and report

Sorts recurring issues by evidence — how often, how many still open, severity, customer impact, recency. Deliberately a tiered sort, not a weighted score, so no invented weights hide inside it.

fully local out: report-365d-v2-*.json
07

Recommend

One AI call per recurring group: what should engineering do about this? Returns a structured recommendation — action type, priority, feasibility, proposal, guardrails. For workflows, a deterministic 0–100 score is computed first, and the AI is never shown it.

Anthropic · 40 + 28 calls out: recommendations-365d-*.json
08

Assemble the review

Joins both tracks into one leadership document: overview, top automation opportunities, recurring workflows, recurring technical issues, long tail, next actions. Validates that every input covers the same window and that recommendations trace to the exact files being used.

fully local · zero API out: review-365d-*.json
09

Render the Slack preview

Produces the exact five messages that would be posted, as an immutable file. Rewrites benefit sentences deterministically from stored evidence, and refuses to build if any unsupported claim (hours saved, money saved, monthly rates) appears in the copy.

fully local · zero API out: review-slack-preview-365d-*.json
10

Publish

Posts the parent message, then the four replies into that thread. Dry-run by default — a live write requires an explicit --publish flag. Resumable, and refuses to publish the same preview twice.

Slack API · write out: publication receipt
06

The three external APIs

The system talks to exactly three services. Everything else is local computation on JSON files.

Anthropic and Voyage — what each one is actually for

This is the question people ask most, so here it is with no jargon at all.

Imagine you have 240 complaint letters and you want to find the ones describing the same problem. You could hand every possible pair to a careful reader and ask "are these two the same?" But 240 letters make 28,680 pairs. That reader would take forever and cost a fortune.

So you do it in two passes:

  1. Voyage sorts the pile roughly. It reads each letter once and gives it a position — letters about billing end up near other letters about billing. Now you can measure instantly, and almost for free, which pairs are even plausibly about the same thing. That cuts 28,680 pairs down to 1,400.
  2. Claude reads the shortlist properly. Only those 1,400 promising pairs go to the expensive reader, who actually decides "yes, same problem" or "no, just similar words".
The one-line difference

Voyage measures whether two sentences look alike. Anthropic decides whether they mean the same thing. Looking alike is cheap and often wrong; meaning the same thing is expensive and correct. The pipeline uses the cheap one to decide what to spend the expensive one on.

Put another way: Voyage never makes a decision. It has no opinion about your business, it cannot tell a bug from a feature request, and it never sees a whole conversation. All it does is turn a sentence into 1,024 numbers so that a computer can sort sentences by resemblance. Every actual judgement in this system — is this technical, are these the same, what should we do — is made by Anthropic or by deterministic code.

And Voyage earns its place purely on cost. Without it, judging every pair would need 28,680 Anthropic calls instead of 1,400 — about 20× the spend — for the technical track alone.

Slack

Used for three separate jobs, each with its own client module — and this separation is a safety feature, not tidiness:

  • src/slack/client.ts — read only. It has no posting method at all. A test asserts the file contains no chat.postMessage call.
  • src/slackPublishing/client.ts — exposes only chat.postMessage.
  • src/slackCleanup/client.ts — exposes only chat.delete.

Because the capability to write simply does not exist in the reading module, a bug in analysis code cannot post to Slack.

Anthropic

Model: claude-haiku-4-5 throughout — a small, fast, cheap model, which is the right choice because every task here is classification or short structured judgement, not long-form generation.

Five distinct prompts, each with its own version number so results can be traced:

PromptVersionJobCalls (365d)
Escalation extractionv3.2Read a thread → structured facts340
Recurrence adjudicationv1Two defects — same issue?1,400
Workflow adjudicationv2Two tasks — same workflow?290
Issue recommendationv1What should engineering fix?40
Workflow recommendationv1What should we automate?28

Total for the full year: about 2,255 calls on the cheapest model.

Voyage AI

A dedicated embeddings provider — this is not Anthropic. Model voyage-4-large, returning 1,024 numbers per sentence, batched 128 at a time.

Real-world gotcha

The account is on Voyage's free tier: 3 requests per minute. Running the technical and workflow embeds back to back triggered an HTTP 429. The fix was to wait 75 seconds and retry. The client has no automatic backoff for 429 yet — worth adding, or adding a payment method to lift the limit.

07

Inside one LLM call

Every AI call in this system goes through the same six-step machine. Understanding this one diagram means understanding all five prompts.

Why step 7 exists: the silent-refinement trap

Zod lets you write cross-field rules like "if this is not a technical escalation, the problem statement must be null". It is tempting to put that in the schema as a .refine().

That silently breaks. Cross-field refinements cannot be expressed in JSON Schema, so the compiler drops them. The rule never reaches the model — but it does still run when validating the reply. The result: perfectly good classifications get rejected client-side for breaking a rule the model was never told about.

So every cross-field rule in this project is enforced in plain code after parsing: enforceNonTechnicalInvariant, enforceWorkflowInvariant, enforceIssueNameInvariant, and so on.

Why step 5 exists: four lost threads

In the 180-day run, 4 of 260 extractions failed because the model returned enum values that did not exist — for example configuration_issue in a field that only accepts workflow types. Strict validation correctly rejected them, but that meant losing the whole thread.

The fix has three parts, and the order matters:

  1. The prompt now lists every allowed value verbatim with an explicit fallback, and a test fails if a schema ever gains a value the prompt does not teach.
  2. Before validation, an invalid value is rewritten to a documented fallback — always an explicit "unknown" bucket (unclear, unknown, other_operational_workflow, or null). Never a guess at a specific category, because a wrong-but-specific value silently corrupts counts while an explicit unknown does not.
  3. Every rewrite is recorded on the result with the field, the raw value, the fallback and the reason — so a normalized field is always auditable.

Dependency injection: why tests cannot reach the network

No business logic imports an SDK. Instead every module takes a function:

type StructuredParseFn<T> = (req: Request) => Promise<Response<T>>;
type VoyageEmbedFn      = (req: Request) => Promise<Vectors>;
type SlackPostFn        = (req: Request) => Promise<{ ts: string }>;
type SlackDeleteFn      = (req: Request) => Promise<{ ok: boolean }>;

The real implementation is wired in only at the CLI entry point. A test passes a fake. This is why all 1,246 tests run in about two seconds with zero API calls and zero cost.

08

The embedding layer

What an embedding actually is

Imagine giving every sentence a location on a map. Sentences about similar things end up near each other. An embedding is that location — except instead of two coordinates it has 1,024, because meaning is more complicated than a map.

Cosine similarity is the angle between two of those locations, expressed from −1 to 1. Around 1.0 means "these point the same way" — very similar wording. Around 0 means unrelated.

Why we do not just cluster on similarity

This is the most important idea in the project, and the easiest to get wrong.

Similarity measures wording overlap, not whether two things are the same problem. Two threads can describe the same defect in completely different words and score low. Two unrelated threads about Stripe can share vocabulary and score high.

The floor is a budget, not a decision

The similarity floor (0.60 technical, 0.80 workflow) only decides which pairs are worth paying an AI to look at. It never decides that two things are the same. That judgement is always made by the adjudication prompt, reading both statements. Pairs at the floor are routinely judged "different".

The workflow floor of 0.80 was not guessed. It was chosen after measuring the real distribution over 10,011 pairs: median 0.3177, mean 0.3392, with only 136 pairs above 0.80. Workflow statements are far more formulaic than defect descriptions, so they needed a higher floor and finer measurement buckets than the technical track.

The privacy gate

Only the short, de-identified statement is ever sent to Voyage. The gate runs before any network call and inspects the exact strings that will be transmitted:

  • Email addresses, Slack permalinks, HubSpot URLs
  • Stripe-style identifiers, UUIDs, Slack user mentions, long numeric IDs

The thread's rootTs and permalink stay on the machine as local metadata and are re-attached after the vectors come back.

09

Grouping: turning pairs into patterns

After adjudication you have thousands of verdicts about pairs. You need groups. This is a graph problem: threads are dots, "same issue" verdicts are lines between them.

The naive approach, and why it failed

The obvious method is connected components: if A links to B and B links to C, put all three in one group. This worked at 90 and 180 days. At 365 days it broke in two opposite directions at once.

The fix: complete-link clique cover

The replacement rule is one sentence: every pair inside a group must have been independently judged the same.

Mechanically it finds all maximal cliques — sets where everyone links to everyone — then claims them greedily, largest first, skipping any that touches an already-assigned thread. Ranking is size, then average confidence, then lowest ID, so the result is identical every run.

This gives four properties for free:

  • No overlap. A thread belongs to at most one group.
  • No chaining. A transitive path cannot form a group.
  • No contradictions. A "different" pair has no link, so it can never be inside a clique.
  • Deterministic. Same verdicts always produce the same groups.
MetricBefore (v1)After (v2)
Technical groups8440
Distinct threads inside them131100
Inflation factor1.76×1.00×
Threads in more than one group540
Distinct issue names71 of 8440 of 40

The trade is deliberate: complete-link favours precision over recall. Nineteen technical threads that have some similarity evidence now sit outside any group rather than being forced in. The evidence is still in the adjudication file if you want it.

Important nuance

A missing adjudication is not treated as "different". Only pairs actually judged the same create links, and candidate generation only ever asked about pairs above the floor. The rule is built around the evidence that exists, not evidence that was never collected.

10

Scoring and ranking

Two different ranking systems, deliberately, because the two tracks need different things.

Technical: tiered sorting, no score

Recurring defects are sorted by a sequence of tie-breakers — occurrence count, then open count, then peak severity, then customer impact, then recency. No weights, because inventing weights implies a precision the evidence does not have.

Workflow: an explicit 0–100 formula

baseScore = 0.30 × frequency
          + 0.25 × manualBurden
          + 0.15 × automationReadiness
          + 0.10 × engineeringDependency
          + 0.10 × customerImpact
          + 0.10 × recency

Each factor is itself 0–100:

  • frequency — a saturating log curve, so 2→4 occurrences separates strongly while 30→40 barely moves. Prevents one huge cluster dominating.
  • manualBurden — weighted average over automation status (manual 100, partly 60, unknown 50, already automated 10).
  • automationReadiness — how amenable the workflow shape is to a guarded tool, minus a penalty for each extra classification spanned.
  • engineeringDependency — 50 baseline because it reached the engineering channel at all, plus code-level involvement and privileged access.
  • customerImpact — from extraction records only. With no evidence it is explicitly neutral at 50, never guessed.
  • recency — full marks within 14 days, decaying to zero at 180.
The LLM cannot touch the numbers

The score is computed before the AI is called. Its output schema has no score and no rank field. The payload it receives contains neither. Rank comes from the deterministic sort position. The AI contributes a qualitative automationPriority that sits alongside the score and never reorders it — and there is a test that feeds the model a fabricated score and rank and asserts they are ignored.

This matters because the AI's own priority labels turned out to be useless as a ranking signal: it marked 33 of 40 technical issues "high". When 82% of everything is high priority, the field cannot discriminate. The deterministic workflow score behaved far better: 5 high, 17 medium, 6 low.

The safety model

This system reads a live company Slack channel and writes to another. Several layers exist to make damage structurally difficult rather than merely unlikely.

The truthfulness guard is unusual, and worth explaining

The AI's recommendations contained confident, invented numbers: "eliminate 13 manual state transitions per month" for a cluster observed 16 times in five months; "two manual backend corrections per week (extrapolated)" for two occurrences 18 days apart; "saves ~1–2 hours of backend work per week" from an assumed minutes-per-task nobody measured.

None of that is derivable from anything the pipeline stores. Rather than trying to clean the prose with pattern matching, the Slack benefit sentence is regenerated deterministically from stored counts and dates:

Removes a workflow observed 8 times in 12 months, recurring
across 161 days. All 8 recorded occurrences required manual
intervention.

Every clause traces to a stored field. A separate guard then scans the finished copy for rate claims, hours-saved claims, monetary estimates and the word "extrapolated", and throws rather than publishing.

That guard also caught a false positive of its own: it initially blocked "implement a 24-hour read-only window", which is a legitimate design parameter rather than a savings claim. The pattern now requires a savings verb nearby, and tests pin both directions.

Deleting the old report safely

When the 90-day report needed retiring, the cleanup command was built to be deliberately timid: it reconstructs the exact message timestamps only from local publication receipts. There is no channel search and no text matching anywhere in it, so a human's message or another tool's message is structurally unreachable. It deletes replies first and the parent last, treats "already deleted" as success so it can be safely re-run, and requires an explicit --delete flag.

Artifacts and provenance

Every stage writes a file whose name encodes what it is:

<prefix>-<window>[-v<generation>]-<date>.json

report-365d-v2-2026-08-14.json
   │      │    │       └── when it was generated
   │      │    └────────── generation 2: a better algorithm, same inputs
   │      └─────────────── 365-day window
   └────────────────────── which stage produced it

Why provenance became the hardest problem

Each stage caches results so a re-run does not pay twice. The trouble is that cache keys were built from content identity — a thread ID, a pair ID, a group ID — and those repeat across windows. The same Slack thread appears in the 90-day, 180-day and 365-day datasets with the same ID.

This produced a class of bug that is silent by nature. It was found in three separate stages:

StageCache keyProblemFix
Technical adjudicationpairId + prompt + modelWould reuse 90d verdicts computed on different problem statementsScope to matching extractionsInputFile
Technical recommendationsgroupId + prompt + modelDid reuse 4 recommendations from the 90d fileScope to matching reportInputFile
Workflow adjudicationpairId + prompt + modelWould reuse 180d verdicts in the 365d runScope to matching embeddings file

Two caches were found to be safe by construction and deliberately left alone:

  • Extraction keys on thread ID + prompt version + model. Reuse is legitimate only because it was verified: the 365-day and 180-day fetches ran three minutes apart and all 260 overlapping threads were byte-identical. Same text, same prompt, same model, therefore same answer — and that saved 260 paid calls.
  • Workflow embeddings key on thread ID + the statement itself + model. Because the embedded text is inside the key, a reworded statement automatically gets a new key. 142 vectors were correctly reused.
The generation gap

When the improved grouping produced report-365d-v2-…, the filename parser did not recognise the -v2- segment — so auto-resolution silently fell back to the old v1 file. The pattern now understands generations and sorts by date, then generation, so a better algorithm's output always supersedes the run it replaces.

The tests are not only about correctness of maths. A large share encode safety properties that would otherwise depend on someone remembering:

  • The read-only Slack client contains no posting call — asserted by scanning the source for actual invocations, not just the word.
  • The publisher makes zero calls unless --publish is present — asserted by checking the guard appears before the client is constructed.
  • Mixed technical/workflow embedding batches are rejected.
  • A 90-day technical report is refused inside a 180-day review.
  • A fabricated score and rank from the model are ignored.
  • The transmitted prompt contains no thread ID, permalink or vector.

Several real bugs were caught by tests during development, including a publisher that threw synchronously from a promise-returning method — which would have slipped straight past a .catch() — and test fixtures that used enum values the schema does not accept, hidden by a type cast.

Lessons and design decisions

If you present this project, these are the parts worth talking about — they are the decisions that were not obvious in advance.

1 · Separate the question from the threshold

Similarity picks candidates; a language model makes the judgement. Conflating those would have produced clusters based on vocabulary overlap rather than meaning, and no threshold value could have fixed it.

2 · Let the LLM judge, never let it count

Every number in the final report — occurrences, ranks, scores, dates, spans — is computed deterministically. The model contributes classifications and prose. The moment it was allowed to describe quantities, it produced confident fabrications, so the copy is now regenerated from stored evidence and guarded.

3 · Cache keys must encode provenance, not just identity

Three separate stages had caches keyed on IDs that legitimately repeat across datasets. Each would have silently served stale results. This is the bug class to look for first in any multi-dataset pipeline.

4 · Precision beats recall for a leadership report

Complete-link grouping leaves some threads ungrouped. That is the right trade when a person will read the output and act on it: an inflated count that names the same issue five times destroys trust faster than a conservative count that misses a few.

5 · Make unsafe things impossible, not merely discouraged

The read-only client has no posting method. The destination channel is a hard-coded constant with no CLI override. The cleanup tool has no way to discover a message. These are cheaper and more reliable than remembering to be careful.

6 · Verify assumptions with data before spending money

Before reusing 260 extractions, the two fetch files were hashed thread by thread to confirm the text was identical. Before trusting the 0.80 workflow floor, the full similarity distribution was measured. Before publishing, the group graph was inspected and two quality failures were found. Each check took minutes and prevented a bad, expensive outcome.

Known gaps

  • The Voyage client has no automatic backoff for HTTP 429 — a rate-limit failure requires a manual retry.
  • Long stages buffer all output and write their artifact only at the end, so a crash mid-run loses the work with no resume point.
  • Complete-link grouping leaves 19 technical threads with real evidence outside any group. Recovering some of that recall would need a "matches most members" rule, which reintroduces a threshold judgement.
  • The generic manual_backend_correction classification covers 98 threads and is doing too much work; display titles now derive from the workflow statement to compensate.
